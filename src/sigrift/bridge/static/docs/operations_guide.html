Operations Guide

System architecture, operational workflows, background tasks, security configuration, and day-to-day procedures for The Bridge.

System Overview & Architecture

System Overview

The Bridge is the central controller in a distributed RF signal intelligence platform. Edge nodes perform RF scanning and send detection data to The Bridge, which stores, scores, correlates, and presents the results through a web dashboard and REST/WebSocket APIs.

Data Flow

Understanding the end-to-end detection pipeline is critical for troubleshooting and tuning:

  1. Edge scanning: rf_scan.py captures IQ samples from SDR hardware, runs signal classification, and produces detection records (frequency, power, SNR, signal class, confidence).
  2. Batching & upload: detection_reporter.py accumulates detections into batches, gzip-compresses them, and uploads via POST /api/detections/batch. If the Bridge is unreachable, the SAF buffer stores batches locally for later replay.
  3. Ingest processing: The Bridge validates the batch, verifies the API key and node binding, inserts rows into the detections table, and runs the anomaly scoring pipeline.
  4. Anomaly scoring: Each detection is evaluated against per-frequency baselines using a composite scorer with configurable dimension weights (power deviation, SNR anomaly, class rarity, time-of-day, Isolation Forest, CUSUM changepoints, MAD scores).
  5. Alerting: Detections exceeding the anomaly threshold trigger alert rules, WebSocket broadcasts to /ws/anomalies, and optional webhook delivery.
  6. Correlation: Cross-protocol correlations (WiFi + BT + RF + Zigbee) are computed to identify multi-band activity from the same source.
  7. Summarization: Hourly rollups aggregate raw detections into compact summaries for long-term trend analysis.

Storage Model

The Bridge uses a single SQLite database (detections.db) in WAL mode, managed through a SharedContext that handles connection pooling, migrations, and PRAGMA configuration.

Edge Node Operations

Deploying an Edge Node

Each edge node runs a lightweight Python agent that manages SDR hardware, detection, and communication with The Bridge.

Prerequisites

  • Linux host (Raspberry Pi 4/5, x86, or similar) with Python 3.11+
  • RTL-SDR or HackRF hardware connected via USB
  • Network connectivity to The Bridge server (port 8443/TCP)
  • API key with sensor role (created via POST /api/keys)

Configuration

# Required environment variables
export MLRF_BRIDGE_URL=https://bridge.example.com:8443
export MLRF_API_KEY=<sensor_api_key>
export MLRF_NODE_ID=edge-01

# Optional tuning
export MLRF_SCAN_INTERVAL=5           # seconds between scans (default: 5)
export MLRF_BATCH_SIZE=50             # detections per upload batch (default: 50)
export MLRF_SPECTRUM=1                # enable spectrum data reporting
export MLRF_BRIDGE_CA_BUNDLE=/etc/ssl/bridge-ca.pem  # custom CA for self-signed certs

Starting the Agent

# Start the edge node agent
python -m sigrift.edge.node_agent

# Or via systemd (recommended for production)
sudo systemctl enable mlrf-edge
sudo systemctl start mlrf-edge

Updating Edge Nodes

Edge nodes can be updated remotely via the node command system:

# Push an update command to a specific node
curl -X POST -H "X-API-Key: $MASTER_KEY" -H "Content-Type: application/json" \
  -d '{"command":"update","params":{"version":"4.1.0"}}' \
  https://bridge.example.com/api/nodes/edge-01/command

For ONNX model updates, the Bridge serves edge-optimized models via GET /api/admin/edge-models with SHA-256 hash verification.

Monitoring Edge Nodes

Node health is tracked through heartbeats. Status transitions:

StatusCondition
activeHeartbeat received within the last 2 minutes
staleNo heartbeat for 2–5 minutes
offlineNo heartbeat for more than 5 minutes

Monitor via:

  • Dashboard: Summary tab shows node status counts and the Deployment tab lists all nodes
  • API: GET /api/nodes/ returns all nodes with status
  • WebSocket: /api/nodes/ws/status pushes real-time state changes
  • Activity log: GET /api/nodes/activity shows recent node events

Store-and-Forward Buffer

The edge detection reporter includes a SQLite-backed Store-and-Forward (SAF) buffer that ensures no detections are lost during network outages:

  • When upload to The Bridge fails after retries, the batch is written to a local SQLite database (saf_buffer.db) in WAL mode
  • A replay loop runs every 60 seconds, attempting to send buffered batches in order
  • Replay stops on the first failure to preserve ordering
  • Batches older than 72 hours are automatically purged
Monitoring SAF: Check saf_buffer.db file size on the edge node. A growing file indicates persistent connectivity issues. The reporter logs SAF buffer depth at each replay attempt.

Summarization Pipeline

Pipeline Overview

The summarization pipeline reduces storage requirements and improves query performance by rolling up raw detections into hourly aggregates. Two modes are supported:

  1. Edge-side summarization: The edge node pre-aggregates detections into hourly summaries and sends them via POST /api/detections/ingest-summary. This reduces bandwidth usage significantly and is recommended for bandwidth-constrained deployments.
  2. Server-side rollup: The Bridge's periodic cleanup task runs rollup_from_raw on the detection_summaries_hourly table, aggregating raw detections from nodes that do not use edge-side summarization. Rollup covers the last 2 hours of data.

Summary records include: node ID, signal class, frequency bucket, hour timestamp, detection count, min/max/avg power, min/max/avg SNR, max anomaly score, and max confidence.

Enabling Edge-Side Summarization

# On the edge node:
export MLRF_SUMMARIZE=1                # enable edge summarization
export MLRF_SUMMARY_INTERVAL=3600      # rollup interval in seconds (default: 3600)

When enabled, the edge node sends both raw detections (for real-time alerting) and hourly summaries (for trend analysis). The Bridge deduplicates summary records on the (node_id, signal_class, freq_bucket_hz, hour_ts) composite key.

Monitoring the Pipeline

  • Ingest status: GET /api/detections/ingest-status shows per-node ingest rates and whether summary data is being received
  • Background task logs: The periodic cleanup logs det_summary_rollup: N rows rolled up each cycle
  • Database stats: GET /api/admin/stats includes row counts for detection_summaries_hourly

Troubleshooting

Detection & Anomaly Workflow

Detection Flow: Edge to Alert

When a batch of detections arrives at POST /api/detections/batch, the following processing occurs:

  1. Authentication: API key validated; node ID binding enforced (key must be authorized for the submitting node)
  2. Decompression: If gzip-compressed, the payload is decompressed (max 50 MB decompressed)
  3. Insertion: Each detection is inserted into the detections table with a timestamp, node ID, and tenant scope
  4. Anomaly scoring: The composite scorer evaluates each detection and produces an anomaly score (0.0–1.0)
  5. Threshold check: If the score exceeds the configured threshold, an RF anomaly record is created
  6. Alert evaluation: Active alert rules are checked against the new anomaly
  7. WebSocket broadcast: Connected dashboard clients receive real-time updates via the detection feed and anomaly stream
  8. Webhook delivery: Matching webhook rules trigger HTTP callbacks (with retry queue for failures)

Anomaly Scoring Pipeline

The composite scorer combines multiple anomaly dimensions, each with a configurable weight:

DimensionMethodDescription
Power deviationMAD / z-scoreHow far the signal power deviates from the frequency baseline. Uses MAD when 30+ samples available, z-score otherwise.
SNR anomalyMAD / z-scoreSignal-to-noise ratio deviation from baseline
Class rarityLaplace-smoothed probabilityHow uncommon this signal class is at this frequency
Time-of-daySin/cos encodingWhether this signal is unusual for the current hour and day-of-week
Isolation ForestUnsupervised modelMulti-dimensional outlier detection across all feature dimensions (13-dim feature vector)
CUSUMCumulative sumDetects sustained shifts in power/SNR after the baseline learning phase (300+ samples)
CorrelationCross-protocolOptional: boost score when multi-protocol activity correlates (default weight: 0.0)
Tuning: Adjust dimension weights via PUT /api/admin/detection-config. The wifi_anomaly_alert_threshold controls the score above which anomalies are flagged.

Score Calibration

The score calibrator uses per-band Platt scaling (sigmoid fit via gradient descent) to normalize raw scores into consistent probabilities. Bands: sub-1 GHz, ISM 2.4 GHz, ISM 5 GHz, other. Calibration requires at least 30 labeled samples per band.

Drift Detection

The drift detector monitors Isolation Forest scores over a rolling window. When mean scores shift by more than 2 standard deviations from the reference distribution, it signals that the model may need retraining. A 1-hour cooldown prevents alert storms during transitions.

Anomaly Review Workflow

  1. Check anomaly summary: GET /api/detections/anomalies/summary
  2. List active anomalies: GET /api/detections/anomalies?sort=score&order=desc
  3. Re-evaluate against current baselines: Add &reevaluate=true
  4. Review individual anomaly: Check signal class, frequency, node, confidence
  5. Take action:
    • Dismiss false positives: PUT /api/detections/anomalies/{id}/dismiss
    • Snooze temporary: PUT /api/detections/anomalies/{id}/snooze with {"hours": 24}
    • Mark as known: review a linked RF detection, then save PUT /api/detections/anomalies/{detection_id}/baseline
    • Submit feedback: POST /api/detections/anomalies/{id}/feedback with label
  6. Bulk dismiss resolved: POST /api/detections/anomalies/bulk/reeval-dismiss
Auto-resolution: The background stale-anomaly resolver automatically marks low-scoring, frequently-seen anomalies as stale-resolved based on configurable thresholds (rf_auto_snooze_hours, rf_auto_snooze_max_score, rf_auto_snooze_seen_count).

Operator-known RF patterns

Open Alerts → Alert settings to add a rule even before a detection or alert exists. Choose Ignore FM broadcast range… for an editable 88–108 MHz starting range, select a Named RF band and choose Review selected band, or choose Add custom frequency range. Named choices reuse the dashboard’s existing band presets; their displayed MHz bounds are editable starting points, not a statement of regional allocations. These rules suppress RF alerts only. Selecting a WiFi-named range does not change separate Wi-Fi or Bluetooth protocol alerts, and no choice stops capture. Review the band for your region, choose a registered node suggestion (or enter a known node ID) or explicitly select all nodes, then save. Suggestions describe registration, not live capture; a failed suggestion lookup leaves manual entry available. Any modulation is selected by default; power changes do not affect matching. Opening a preset does not enable it. Use Edit to change a saved range or Remove (including the immediate undo action) to enable future matching alerts again.

In the Alerts tab or a detection's RF detail, choose Mark as known. Review the monitored frequency range (initially ±50 kHz), modulation choice, and node. New review forms select Any modulation (frequency only): modulation and power changes still match within that range and node. Uncheck it to match the source signal class instead. Existing patterns keep their saved choice when edited. The current node is selected by default; choosing all nodes explicitly broadens the rule. Add a reason, then save. Only eligible alerts linked to a stored RF detection offer this action; unrelated system, Wi-Fi and Bluetooth alerts do not.

Scanner frequency is the receiver’s tuned center, not a measured transmitter frequency. This option does not automatically learn known frequencies or identify newly occupied channels.

A saved pattern suppresses future matching RF anomaly, condition-rule and watch-band alerts, including their notifications. It does not certify the classification or signal as safe, change scores or learned statistics, dismiss existing alerts, or remove any detection or anomaly records. Existing seeded score reductions are separate and unchanged.

Open Known RF patterns in the Alerts tab to review, edit or remove patterns. The save confirmation also offers immediate removal. Changes are committed with an audit record before success is returned; retrying an identical save cannot create duplicates. A concurrent edit requires a refresh before changing or removing the rule. Removing a rule enables future matching alert evaluation again, subject to normal thresholds and cooldowns; it does not recreate past alerts. Analysts and administrators can change patterns; viewers have read-only access.

Patterns live in the tenant-scoped known_rf_signals table in detections.db and survive restarts and database backups. They are not part of config-only snapshots, the legacy JSON whitelist, or baseline bundle import/export. Rolling back to an older application leaves this additive table and detection data intact, but that application does not enforce the new suppression rules. Legacy bulk baseline requests use the same durable rules and reject an unknown detection without partially saving the batch. The grouped browser action reviews one actual detection, rather than silently applying a rule to every node in an aggregate.

Baseline Learning Phase

When a new frequency is first observed, the scorer enters a learning phase:

  • The first 300 detections use exact online (Welford) variance calculation
  • After 300 samples, the baseline transitions to Exponentially Weighted Moving Average (EWMA) for adaptive tracking
  • During learning phase, scores for baseline-dependent dimensions (power, SNR) are dampened to reduce false positives
  • CUSUM changepoint detection only activates after the learning phase completes
  • MAD scoring requires at least 30 ring buffer samples before becoming the preferred method over z-score

Adaptive frequency binning is used: sub-GHz signals use 25 kHz bins, while signals at 1 GHz and above use 500 kHz bins.

Threat Detection & Incident Response

Threat Signatures

The Bridge maintains a library of known threat signatures that are matched against incoming detections. Each signature defines:

  • Frequency range: Center frequency with tolerance
  • Signal class pattern: Expected modulation/protocol type
  • Power/SNR thresholds: Minimum power level or SNR range
  • Temporal pattern: Expected duration, periodicity, or burst characteristics
  • Severity: Informational, low, medium, high, critical
# List all threat signatures
curl -H "X-API-Key: $KEY" https://bridge.example.com/api/threats/list

# Seed the default signature library
curl -X POST -H "X-API-Key: $MASTER_KEY" https://bridge.example.com/api/threats/seed

# Manually test a detection against signatures
curl -X POST -H "X-API-Key: $KEY" -H "Content-Type: application/json" \
  -d '{"freq_hz":433920000,"signal_class":"fsk","power_dbm":-30,"snr_db":25}' \
  https://bridge.example.com/api/threats/match

See the API Reference: Threat Signatures for full endpoint documentation.

Matching Process

During detection ingest, each detection is compared against active threat signatures. A match produces a signature_match record linking the detection to the signature. High-severity matches can automatically create incidents.

Incident Lifecycle

Incidents follow a state machine: open → investigating → resolved (or closed). Each transition is recorded in the incident timeline.

# Create an incident manually
curl -X POST -H "X-API-Key: $KEY" -H "Content-Type: application/json" \
  -d '{"title":"Unknown 433 MHz transmitter","severity":"high","description":"Persistent FSK signal in secure area"}' \
  https://bridge.example.com/api/incidents/

# Assign to an analyst
curl -X PUT -H "X-API-Key: $KEY" -H "Content-Type: application/json" \
  -d '{"assigned_to":"analyst@example.com"}' \
  https://bridge.example.com/api/incidents/INC-001/assign

# Link detections to the incident
curl -X POST -H "X-API-Key: $KEY" -H "Content-Type: application/json" \
  -d '{"detection_ids":["det-abc","det-def"]}' \
  https://bridge.example.com/api/incidents/INC-001/detections

# Resolve the incident
curl -X PUT -H "X-API-Key: $KEY" -H "Content-Type: application/json" \
  -d '{"resolution":"Identified as authorized maintenance radio"}' \
  https://bridge.example.com/api/incidents/INC-001/resolve

See the API Reference: Incidents for full endpoint documentation.

MFA & Security Configuration

MFA / TOTP Setup

The Bridge supports Time-based One-Time Password (TOTP) multi-factor authentication compatible with any TOTP authenticator app (Google Authenticator, Authy, 1Password, etc.).

Enabling MFA for a User

  1. Generate secret: POST /api/mfa/setup — returns a TOTP secret and QR code URI
  2. Scan QR code: User scans with their authenticator app
  3. Verify setup: POST /api/mfa/verify-setup with the first TOTP code to confirm enrollment
  4. Login flow: After password authentication, a second POST /api/mfa/verify step is required with the current TOTP code

Backup Codes

Backup codes are generated during MFA setup. Each code can be used once as a fallback when the authenticator app is unavailable. Store them securely offline.

Disabling MFA

# Requires a valid TOTP code or backup code to disable
curl -X POST -H "X-Session-Token: $TOKEN" -H "Content-Type: application/json" \
  -d '{"totp_code":"123456"}' \
  https://bridge.example.com/api/mfa/disable
Production requirement: Set BRIDGE_MFA_KEY to a valid Fernet key (base64 of 32 bytes: 44 characters ending in =), e.g. python3 -c 'from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())'. A 43-character secrets.token_urlsafe(32) value is not a valid key: append = to it (do not replace it), which keeps TOTP secrets already encrypted with it readable. In production the bridge and gateway refuse to start if the key is missing or invalid; in development TOTP secrets fall back to base64 encoding only (not encrypted) and the health endpoint reports a security warning.

Session Security

Session tokens are SHA-256 hashed before storage in the database. The raw token is returned to the client only once at login.

Session bindingBRIDGE_SESSION_BINDINGipBind sessions to client IP. Options: ip, warn, none

Password Policy (NIST 800-63B)

  • Minimum 12 characters
  • Checked against a common password blocklist
  • Character variety check (requires mix of character types)

CSRF Protection

The Bridge implements Double Submit Cookie CSRF protection for session-authenticated mutating requests (POST, PUT, PATCH, DELETE).

Env VarDefaultDescription
BRIDGE_CSRFenabled in productionSet to disabled to turn off outside production. Automatically disabled when BRIDGE_ENV is development, dev, or test. In production the bridge (BRIDGE_ENV or BRIDGE_MODE production or prod) and the gateway (BRIDGE_ENV production, prod or unset) refuse to start unless it is unset, empty or enabled. Elsewhere the bridge turns its check off for any other value, the gateway only for exactly disabled.

The CSRF cookie is set at login. The frontend auth_guard.js automatically includes the token in requests. API-key-only requests (no session) are exempt.

Exempt paths: login, logout, MFA verify, version, health, batch ingest. Login and MFA verify instead refuse a body that is not sent as Content-Type: application/json (the gateway answers 415), so a cross-site form cannot sign a browser in.

Data-at-Rest Encryption

SQLCipher database encryption is not supported in this release. Do not set BRIDGE_DB_ENCRYPTION_KEY, even though the health warning still suggests it: if the key reaches the bridge, it refuses to start without pysqlcipher3 (which the shipped images do not include), and with pysqlcipher3 installed it still fails at start-up.

  • Volume-level: Use LUKS/dm-crypt on the storage volume. Then set BRIDGE_ENCRYPTION_KEY in the bridge's environment to acknowledge it and suppress the health warning; with Docker Compose that means an environment: entry in docker-compose.override.yml, because .env alone does not pass it to the bridge.

Encryption status is reported in the GET /api/health response under security_warnings.

Audit Chain Integrity

The audit log uses HMAC-SHA256 chaining: each entry's HMAC covers the previous entry's HMAC plus the current entry's fields (action, target_id, operator, timestamp, details, note, signal_class, freq_hz, node_id). This ensures tamper detection.

  • Legacy entries (before HMAC was introduced) use a sentinel value to prevent chain resets
  • Archive markers preserve the terminal HMAC when old audit entries are archived
  • Verify chain integrity: GET /api/admin/audit/verify

Background Tasks

Task Overview

The Bridge runs several background asyncio tasks during its lifespan. All background tasks can be disabled by setting BRIDGE_BACKGROUND_TASKS=false.

TaskDefault IntervalEnv OverridePurpose
Periodic cleanup30 minBRIDGE_CLEANUP_INTERVALAggregate, purge, and compact data across all stores

WAL checkpoint30 minBRIDGE_WAL_CHECKPOINT_INTERVALPASSIVE WAL checkpoint to move pages to main DB

Periodic Cleanup Details

The cleanup task (default: every 30 minutes) runs the following operations in sequence:

  1. Aggregate WiFi metadata into hourly buckets (rows older than 2 hours)
  2. Purge raw WiFi metadata older than 4 hours (already aggregated)
  3. Purge WiFi anomalies older than retention period
  4. Purge raw detections older than retention period
  5. Purge RF anomalies older than retention period
  6. Purge hourly summaries older than retention period
  7. Compact dismissed WiFi anomalies (keep most recent per BSSID)
  8. Purge old BT devices and anomalies
  9. Purge old Zigbee devices
  10. Clean up expired config snapshots
  11. Clean up security state (rate limits, lockouts, expired OIDC/TOTP records)
  12. Roll up raw detections into hourly summaries (for non-summarizing nodes)
  13. Roll up IQ metadata into capture sessions
  14. Deduplicate FHSS events into summaries
  15. Run device lifecycle daily rollup and archive stale devices

Configure retention with BRIDGE_RETENTION_DAYS=90 (default). Each step uses 10k-row batch deletes to avoid write lock starvation.

Spectrum Materializer

The materializer maintains a pre-computed view of spectrum data (spectrum_all) for fast dashboard queries. It supports both incremental refreshes (new data since last refresh) and full rebuilds.

# Force a full refresh via maintenance API
curl -X POST -H "X-API-Key: $MASTER_KEY" -H "Content-Type: application/json" \
  -d '{"task":"refresh_spectrum_view"}' \
  https://bridge.example.com/api/admin/maintenance

Other Background Tasks

Stale Anomaly Resolver

Automatically marks RF anomalies as stale-resolved when they meet all of these criteria:

  • Anomaly is older than rf_auto_snooze_hours (default: 24)
  • Score is below rf_auto_snooze_max_score (default: 0.5)
  • Detection has been seen at least rf_auto_snooze_seen_count times (default: 100)

These thresholds are configurable via detection config.

Admin Password Auto-Delete

If an initial admin password file is used at startup, it is automatically deleted after 60 seconds for security.

Disabling / Tuning Background Tasks

# Disable all background tasks (useful for testing or read-only replicas)
export BRIDGE_BACKGROUND_TASKS=false

# Tune specific intervals (seconds)
export BRIDGE_CLEANUP_INTERVAL=1800
export BRIDGE_MATERIALIZER_INTERVAL=300
export BRIDGE_WAL_CHECKPOINT_INTERVAL=1800
export BRIDGE_STALE_RESOLVE_INTERVAL=600

Spectrum & Geolocation

Interpreting the Spectrum Waterfall Display

The spectrum waterfall provides a time-frequency view of all RF activity detected by edge nodes. Each row represents a time slice; the horizontal axis maps to frequency, and colour intensity indicates signal power.

  • Bright horizontal lines: Persistent signals (e.g. broadcast FM, cellular carriers). These are normal in most environments.
  • Short bright bursts: Intermittent transmissions such as push-to-talk radio, IoT uplinks, or radar pulses.
  • Wideband blocks: OFDM or spread-spectrum signals (WiFi, LTE). The width corresponds to channel bandwidth.
  • Colour scale: Power in dBm. Use the range slider above the waterfall to adjust the colour floor and ceiling for better contrast.
# Fetch raw spectrum data for a specific node and time range
curl -H "X-API-Key: $KEY" \
  "https://bridge.example.com/api/spectrum/waterfall?node_id=rooftop-01&hours=1&resolution=256"
Tip: Narrow the frequency range with freq_min and freq_max query parameters to focus on a specific band.

Band Occupancy Analysis

Band occupancy shows the percentage of time each frequency band is active, helping identify congested or under-utilised spectrum.

  • View occupancy chart: Navigate to Spectrum → Band Occupancy in the dashboard or query the API directly.
  • Time resolution: Occupancy is computed over configurable intervals (default: 15 minutes). Shorter intervals provide finer granularity at the cost of more data.
  • Threshold: A frequency bin is considered "occupied" when the detected power exceeds the noise floor by the configured margin (default: 6 dB above baseline).
# Query band occupancy for the ISM 433 MHz band
curl -H "X-API-Key: $KEY" \
  "https://bridge.example.com/api/spectrum/occupancy?freq_min=433e6&freq_max=434e6&hours=24"

# Get occupancy summary across all monitored bands
curl -H "X-API-Key: $KEY" \
  "https://bridge.example.com/api/spectrum/occupancy/summary"

Troubleshooting

Node Disconnected / Stale

Symptoms: Node shows "stale" or "offline" status in dashboard.

  • Check network connectivity from edge node to Bridge server
  • Verify API key is valid: curl -H "X-API-Key: $NODE_KEY" https://bridge/api/health
  • Check edge node logs for connection errors or SSL certificate issues
  • Verify SSL: If using self-signed or internal CA certs, set BRIDGE_CA_BUNDLE=/path/to/ca.pem on edge
  • Check firewall: Port 8443 must be open between edge and Bridge
  • Monitor heartbeats: Node status transitions from active to stale after 2 minutes, then offline after 5 minutes without heartbeat
  • Check SAF buffer: If the edge node's saf_buffer.db is growing, the node cannot reach the Bridge

High Anomaly Scores / Alert Storms

Symptoms: Flood of anomaly alerts, high anomaly counts.

  • Check if a new signal source appeared: Review frequency and signal class in anomaly details
  • Re-evaluate against baselines: GET /api/detections/anomalies?reevaluate=true — many anomalies may now be resolved
  • Bulk dismiss resolved: POST /api/detections/anomalies/bulk/reeval-dismiss
  • Adjust thresholds: PUT /api/admin/detection-config to tune wifi_anomaly_alert_threshold, dimension weights
  • Whitelist known APs: Add to WiFi whitelist via admin panel
  • Alert cooldown: Per node and 100 kHz frequency bucket, a warning anomaly alert waits 5 minutes after the bucket's last alert and a critical one waits 60 seconds, so a source that stays critical can alert once a minute
  • Check learning phase: A new frequency baseline needs ~300 detections before scoring stabilizes. False positives during learning are dampened but not eliminated.

Database Growth

Symptoms: Large detections.db file, slow queries.

# Check database stats
curl -H "X-API-Key: $MASTER_KEY" https://bridge.example.com/api/admin/stats

# Run full cleanup (purge + vacuum)
curl -X POST -H "X-API-Key: $MASTER_KEY" -H "Content-Type: application/json" \
  -d '{"task":"full_cleanup","retention_days":30}' \
  https://bridge.example.com/api/admin/maintenance

# Or use the retention policy purge
curl -X POST -H "X-API-Key: $MASTER_KEY" -H "Content-Type: application/json" \
  -d '{"task":"purge_old_data","retention_days":90}' \
  https://bridge.example.com/api/admin/maintenance

Automatic cleanup: The Bridge runs periodic cleanup every 30 minutes. Configure retention with BRIDGE_RETENTION_DAYS (default: 90).

WAL file growth: WAL is checkpointed automatically every 30 minutes (PASSIVE mode). Force checkpoint: {"task":"wal_checkpoint"}

Disk space monitoring: The health endpoint (GET /api/health) reports disk_usage_pct and warns at 80%/90%.

WebSocket Connection Issues

Symptoms: Dashboard shows "disconnected", WebSocket connections dropping.

  • Check rate limits: Max 10 concurrent WS connections per IP, 30/minute
  • Verify auth method: Use Sec-WebSocket-Protocol: bridge-v1, API_KEY header (not query params)
  • Proxy configuration: Ensure nginx/reverse proxy supports WebSocket upgrade and has adequate proxy_read_timeout
  • Network issues: WebSockets need persistent TCP connections; check for intermediate proxies/firewalls

Authentication Failures

  • 401 "API key required": Missing X-API-Key header or api_key query param
  • 401 "Invalid API key": Key not found or expired. Check key list: GET /api/admin/keys ("expired": true for a key bridge auth rejects as expired, also when its stored expires_at cannot be parsed; effective_expires_at is the instant it applies). A key that works on bridge routes but gets 401 from the gateway's own routes (users, sessions, audit) may hold a hand-edited expires_at the gateway cannot read, such as 2999-01-01T00:00: rewrite it as 2999-01-01T00:00:00+00:00
  • 403 "Admin role required": Key has insufficient role. Upgrade via PUT /api/admin/keys/{id}/permissions
  • 429 "Rate limit exceeded": Too many requests. Wait for Retry-After seconds. Admin endpoints: 10/min
  • 423 "Account locked": Too many failed login attempts. Lockout lasts 30 minutes. An admin can clear lockouts via the admin panel.

Slow Queries

  • Run PRAGMA optimize: {"task":"optimize"}
  • Check WAL size via GET /api/admin/stats — large WAL indicates need for checkpoint
  • Reduce query scope: use node_id, time range, and limit filters
  • Aggregate old data: {"task":"aggregate_detections"}

Map Not Loading

Symptoms: Geo map page is blank, tiles not rendering, or nodes not appearing on the map.

  • Check browser console: Look for JavaScript errors or failed tile requests. Tile servers may be unreachable if the Bridge host has no internet access.
  • Offline tile support: For air-gapped deployments, configure a local tile server or use the built-in offline tile cache (set GEO_TILE_URL to a local endpoint).
  • No nodes on map: Verify that at least one node has a location set: GET /api/geo/nodes. Nodes without latitude/longitude are excluded from the map.
  • CORS issues: If serving tiles from a different origin, ensure the tile server sends appropriate Access-Control-Allow-Origin headers.
  • WebGL errors: Some heatmap renderers require WebGL. Check browser compatibility or disable GPU acceleration as a workaround.

Spectrum Data Empty

Symptoms: Waterfall display shows no data, band occupancy charts are blank.

  • Verify spectrum ingest: Check that edge nodes are sending spectrum data: GET /api/spectrum/status. If last_sweep is null, the node is not reporting spectrum.
  • Check node agent config: Ensure the edge agent is configured with MLRF_SPECTRUM=1 (spectrum reporting is disabled by default to save bandwidth).
  • Time range mismatch: The waterfall defaults to the last hour. If spectrum data is older, adjust the hours parameter.
  • Frequency range: If freq_min/freq_max filters are set too narrowly and no signals fall within that range, the display will be empty.
  • Storage retention: Spectrum data is subject to the same retention policy as detections. Old sweeps may have been purged by the hourly cleanup.

Scheduled Maintenance

Database Vacuum

SQLite VACUUM reclaims disk space from deleted rows. Run periodically (weekly) or after large purges.

curl -X POST -H "X-API-Key: $MASTER_KEY" -H "Content-Type: application/json" \
  -d '{"task":"vacuum","retention_days":1}' \
  https://bridge.example.com/api/admin/maintenance
Note: VACUUM temporarily doubles disk usage and blocks all writes. Schedule during low-activity periods.

WAL Checkpoint

The Bridge runs PASSIVE WAL checkpoints every 30 minutes automatically. For a forced checkpoint:

curl -X POST -H "X-API-Key: $MASTER_KEY" -H "Content-Type: application/json" \
  -d '{"task":"wal_checkpoint","retention_days":1}' \
  https://bridge.example.com/api/admin/maintenance

Retention Cleanup

The automatic cleanup (every 30 min) performs aggregation, purge, and compaction across all data stores. See Periodic Cleanup Details for the full sequence.

Configure with BRIDGE_RETENTION_DAYS=90 (default).

Log Rotation

The Bridge uses an in-memory ring buffer for logs (viewable via GET /api/admin/logs). For persistent log files, configure your process manager (systemd, Docker) to rotate stdout/stderr. With JSON logging (BRIDGE_LOG_FORMAT=json), use standard log aggregation tools.
