Deployment Guide

Complete guide to deploying The Bridge RF signal detection backend and edge nodes.

Prerequisites

  • Python 3.10+ (3.11 or 3.12 recommended)
  • SQLite 3.35+ (for VACUUM INTO support; ships with Python 3.10+)
  • pip or uv package manager
  • Linux (Ubuntu 22.04+, Debian 12+, or Raspberry Pi OS for edge nodes)
  • 2GB+ RAM for the Bridge server, 512MB+ for edge nodes
  • Edge nodes: RTL-SDR dongle

Installation

# Clone the repository
git clone https://github.com/SigRift/SigRift.git
cd SigRift

# Create virtual environment
python3 -m venv .venv
source .venv/bin/activate

# Install dependencies
pip install -e .
# Or with uv:
# uv pip install -e .

YAML Configuration

The Bridge loads configuration from SigRift/config.py with dataclass defaults. Key sections:

  • SecurityConfig: rate_limit_per_minute (default: 300), tls_enabled, require_auth, api_key_length (32), max_request_size_mb (10)
  • TrainingConfig: Epochs, batch size, learning rate, early stopping, SNR ranges
  • HardwareConfig: Sample rate, capture settings
  • ModelConfig: Architecture parameters (base_channels, num_classes=40, dropout)

Bridge Server Setup

Starting the Server

# Development mode
uvicorn sigrift.bridge.app:app --host 0.0.0.0 --port 8443 --ssl-keyfile key.pem --ssl-certfile cert.pem

# Production with multiple workers
uvicorn sigrift.bridge.app:app --host 0.0.0.0 --port 8443 \
  --ssl-keyfile /etc/ssl/bridge/key.pem \
  --ssl-certfile /etc/ssl/bridge/cert.pem \
  --workers 1 --limit-concurrency 100
Important: Use only 1 worker for SQLite (no multi-process write support). For higher throughput, use a reverse proxy with connection pooling.

[Install]
WantedBy=multi-user.target
sudo systemctl daemon-reload
sudo systemctl enable bridge
sudo systemctl start bridge

Reverse Proxy (nginx)

# /etc/nginx/sites-available/bridge
upstream bridge {
    server 127.0.0.1:8443;
}

server {
    listen 443 ssl http2;
    server_name bridge.example.com;

    ssl_certificate /etc/ssl/bridge/fullchain.pem;
    ssl_certificate_key /etc/ssl/bridge/privkey.pem;

    # Security headers (Bridge also sets these)
    add_header X-Content-Type-Options nosniff;
    add_header X-Frame-Options DENY;

    # Request size limit (Bridge enforces 10MB)
    client_max_body_size 10m;

    location / {
        proxy_pass https://bridge;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }

    # WebSocket endpoints
    location ~ /ws/ {
        proxy_pass https://bridge;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_read_timeout 86400;
    }

    # Static files with caching
    location /static/ {
        proxy_pass https://bridge;
        proxy_cache_valid 200 1h;
    }
}

SSL/TLS Configuration

# Generate self-signed certificate (development)
openssl req -x509 -newkey rsa:4096 -keyout key.pem -out cert.pem -days 365 -nodes \
  -subj "/CN=bridge.local"

# Let's Encrypt (production)
certbot certonly --standalone -d bridge.example.com

When using self-signed or internal CA certs, set BRIDGE_CA_BUNDLE=/path/to/ca.pem on edge nodes to provide the CA certificate for verification.

Edge Node Overview

Each edge node runs:

  1. RTL-SDR capture → raw IQ samples at 2.048 MHz
  2. Inference engine → ONNX Runtime classification
  3. Detection Reporter → batches and uploads detections to the Bridge
  4. WiFi Scanner (optional) → 802.11 metadata collection

Detection Reporter Configuration

# Run the detection reporter
python -m sigrift.edge.detection_reporter \
  --server-url https://bridge.example.com:8443 \
  --api-key YOUR_SENSOR_KEY \
  --node-id node-01 \
  --min-confidence 0.5 \
  --min-snr 3.0 \
  --batch-size 100

# Or use environment variables:
export MLRF_BRIDGE_URL=https://bridge.example.com:8443
export MLRF_API_KEY=YOUR_SENSOR_KEY
export MLRF_NODE_ID=node-01
python -m sigrift.edge.detection_reporter

The reporter supports:

  • Gzip compression of batch uploads
  • Automatic retry with exponential backoff
  • Deduplication of repeated detections
  • Configurable confidence and SNR thresholds
  • IQ capture uploads for anomalous detections

WiFi Scanner Setup

The WiFi scanner collects 802.11 metadata and submits via POST /api/wifi/ingest. Requires monitor-mode capable WiFi adapter.

SigRift Gateway Sidecar

The SigRift gateway (sigrift-gateway) is a Rust microservice that fronts The Bridge's Python backend. It handles batch detection ingest, real-time anomaly scoring, read-only dashboard queries, and WebSocket feed broadcasting — all backed by the same shared SQLite database.

In the single-host default deployment (see docker-compose.yml) the gateway terminates TLS on 8444 and proxies non-native routes to the bridge on 8001.

Build & Install

Requires Rust 1.75+ (stable toolchain).

# Build the release binary
cd SigRift
cargo build --release -p sigrift-gateway

# The binary is at target/release/sigrift-gateway
# Copy to your deployment path:
sudo cp target/release/sigrift-gateway /usr/local/bin/sigrift-gateway

Bridge Integration

The gateway shares The Bridge's SQLite database and API key store. The Python Bridge app validates auth via the same keys.json, while the gateway reads the same file for its own API key verification (fail-closed: if the keys file is missing, all authenticated requests are rejected).

Reverse Proxy (optional)

For multi-host or production deployments terminating TLS upstream (e.g. nginx/Caddy with a real certificate), route all traffic to the gateway on 8444 and let it handle the internal proxy to the bridge:

# nginx example — single upstream, gateway handles internal routing
location / {
    proxy_pass https://127.0.0.1:8444;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
}

API Key Management

Initial Master Key

On first startup with an empty key store, The Bridge auto-generates a master key:

  • If BRIDGE_MASTER_KEY is set, that value is used
  • Otherwise, a random key is generated and written to data/.master_key (chmod 600)
Production: Always set BRIDGE_MASTER_KEY in the environment. Never rely on the auto-generated file in production.

Creating Keys

# Create a sensor key for an edge node
curl -X POST -H "X-API-Key: $MASTER_KEY" -H "Content-Type: application/json" \
  -d '{"description":"Node 01 sensor","role":"sensor","expires_days":365}' \
  https://bridge.example.com/api/admin/keys

# Create a viewer key for dashboard access
curl -X POST -H "X-API-Key: $MASTER_KEY" -H "Content-Type: application/json" \
  -d '{"description":"Dashboard viewer","role":"viewer"}' \
  https://bridge.example.com/api/admin/keys

Deployment Status and Optional SSH Audit

The Deployment tab shows node contact and current scanner reports without SSH setup. A scanner can report normally while its optional SSH audit is unconfigured or fails. Reports expire after 120 seconds; recent node contact alone does not prove that a scanner is capturing. Refresh updates these report lifetimes even when host audit results are cached.

Normal quickstart needs no SSH keys or host-key changes. Its local-edge node advertises the application service name edge; that does not imply an SSH server exists there. A registered node address is never automatically used as an SSH target.

For an advanced host audit, provide a separate operator-owned JSON file and set BRIDGE_DEPLOYMENT_SSH_CONFIG to its path inside the Bridge container. For example:

{
  "remote-node": {
    "host": "scanner-host.example",
    "user": "audit",
    "port": 22,
    "known_hosts_file": "/app/ssh-audit/known_hosts",
    "identity_file": "/app/ssh-audit/identity"
  }
}

Use a host and port reachable from the Bridge, an explicitly authorized audit account, and absolute file paths without whitespace. Mount the target file, verified known_hosts and the existing audit identity read-only and make them readable by the Bridge user (UID 1500 in the shipped image). Do not upload keys in node registration, paste them into the dashboard, or overwrite an existing Compose override. Merge these additions into the operator-managed Bridge service configuration:

services:
  bridge:
    environment:
      BRIDGE_DEPLOYMENT_SSH_CONFIG: /app/ssh-audit/targets.json
    volumes:
      - ./ssh-audit:/app/ssh-audit:ro

Verify the SSH host fingerprint through a trusted channel before provisioning known_hosts. The audit enforces strict verification and ignores ambient SSH configuration; it never accepts a new or changed key automatically. An unverified host key, changed key, unavailable identity, DNS failure or timeout has a separate actionable status. Scanner API credentials are not SSH credentials.

Existing SSH deployments: configure targets explicitly when upgrading. The old implicit pi@node.host behavior and BRIDGE_SSH_HOST_KEY_CHECKING overrides are no longer used by this audit. No node registration, credential or host setting is changed automatically.

Host auditing retains the existing Linux/systemd layout checks; it is not Docker container inspection. SSH results are cached for five minutes, with at most four concurrent processes per request, ten seconds per target, and 32 configured targets. A fresh status response does not certify reachability, package consistency or radio operation. Refreshing scanner-only installations does not start SSH processes.

Backup & Restore

Database Backup

# Create a backup via API
curl -X POST -H "X-API-Key: $MASTER_KEY" \
  https://bridge.example.com/api/admin/backup

# List available backups
curl -H "X-API-Key: $MASTER_KEY" \
  https://bridge.example.com/api/admin/backups

# Download a backup
curl -H "X-API-Key: $MASTER_KEY" -o backup.db \
  https://bridge.example.com/api/admin/backups/detections_backup_20260214_120000.db

Persistence Directory

The data/ directory contains all persistent state:

  • detections.db — SQLite database (detections, anomalies, audit log, WiFi metadata)
  • .master_key — Auto-generated master key file
  • baselines.json — RF anomaly baseline data
  • wifi_baselines.json — WiFi anomaly baseline data
  • iq_captures/ — IQ waveform captures
  • pcap_captures/ — WiFi pcap captures
  • backups/ — Database backup copies

Back up the entire data/ directory regularly. The persistence manager also saves node registrations, alerts, and key metadata to JSON files.

Logging

Log Levels

Set via BRIDGE_LOG_LEVEL environment variable. In production, use INFO (default).

JSON Logging

Set BRIDGE_LOG_FORMAT=json for structured JSON output, suitable for log aggregation (ELK, Loki, etc.).

In-App Log Viewer

Access recent logs via the admin API: GET /api/admin/logs. Supports filtering by level, logger name, and full-text search.
